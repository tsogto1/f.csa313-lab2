## SLO ба тайлбар

Алхам 2-т 5 VU-ын baseline тестээр хэмжсэн p95 = 101.87 ms гарсан. Локал сервер `sleep(0.1)` ашигладаг тул хамгийн бага боломжит хариу цаг ойролцоогоор 100 ms байх ёстой — энэ нь biед baseline-тай нийцэж байна. SLO-г тогтоохдоо системийн бага зэргийн savoir хэлбэлзэл болон дараагийн үе шатны ачааллын дор (30 VU) queue үүсэхийг тооцож, threshold-оо baseline-аас ойролцоогоор 5 дахин өндөр (p95 < 520 ms) байхаар сонгосон. Ингэснээр хэвийн ачааллын үед (5 VU) найдвартай PASS хийх боловч дунд/өндөр ачааллын үед (30, 100 VU) latency доройтлыг мэдрэмжтэй илрүүлэх чадвартай хэвээр байна. Error rate-ийн хувьд лекцийн стандарт SLO жишээ болох rate < 1%-ийг шууд авсан.

## Дүгнэлт (8-10 өгүүлбэр)

5 VU-ийн тестэд систем маш тогтвортой ажиллаж, p95 = 101.87 ms, алдааны хувь 0% гарч хоёр threshold бүгд PASS болсон. 30 VU-д throughput 9.43 req/s хүртэл өссөн боловч p95 latency 1.1 секунд хүртэл ойролцоогоор 10 дахин удаашарч, duration threshold зөрчигдсөн — гэхдээ алдааны хувь 0% хэвээр байсан нь сервер хүсэлтийг татан авахгүй, харин удаан боловч бүрэн боловсруулж байсныг харуулж байна. 100 VU-д систем даацандаа дийлэхгүй болж, throughput 3.52 req/s хүртэл буурч (буурсан!), p95 56.94 секунд буюу timeout-д ойрхон утга гарч, алдааны хувь 33.75% хүртэл огцом өссөн. Энэ зураглал нь локал серверийн single-threaded (`HTTPServer`) архитектур улмаас хүсэлтүүд дараалалд орж, latency геометр прогрессоор өссөнийг тод харуулж байна. Лекц 2-т үзсэн "ачаалал өсөхөд latency, error rate муудаж, throughput тодорхой цэгээс хойш буурдаг" зарчим энэ хэмжилтээр бүрэн нотлогдсон. Мөн p95 нь дундаж утгаас (avg) хамаагүй илүү risk-ийг илрүүлж чадсан — жишээ нь 100 VU-д avg=10.44s байхад p95=56.94s болж, "хэрэглэгчийн ихэнх хувь сайн, цөөхөн хувь маш муу туршлагатай байх" эффектийг харуулсан. Availability буюу checks_succeeded метр 100%→100%→66.24% болж алгуур буурсан нь SLO зөрчигдөхийн зэрэгцээ хэрэглэгчийн бодит туршлага ч мөн муудсаныг баталж байна. Бидний тогтоосон SLO (p95 < 520 ms, error rate < 1%) зөвхөн 5 VU-ийн түвшинд бүрэн хангагдсан бол 30 болон 100 VU-д зөрчигдсөн. Иймд энэ систем нь одоогийн хэлбэрээрээ ойролцоогоор 5-10 зэрэгцээ хэрэглэгч хүртэл найдвартай ажиллах бөгөөд түүнээс дээш ачаалалд тогтвортой ажиллуулахын тулд threading (`ThreadingHTTPServer`) эсвэл horizontal scaling шаардлагатай гэж дүгнэж болно.
